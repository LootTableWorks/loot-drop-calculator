Guide 01

World architecture

7 min read

Dependency-closed world seeds

A world seed is useful only when every referenced thing arrives with it.

A generated town can sound complete while quietly depending on missing items, locations, enemies, or rewards. A dependency-closed seed treats the result as a small graph: every selected record is a node, every reference is an edge, and every edge must end at another included node.

1. Start from a playable question

Choose the smallest loop you need to test. “Can the player buy a remedy, learn where its ingredients come from, and earn one through play?” is more useful than “generate a coastal town.” The question tells you which record types belong in the seed.

2. Expand references, not vibes

When a merchant stocks an item, include the exact item record. When a recipe consumes that item, include the recipe and every other required ingredient. When a quest awards the recipe output, include the quest, its location, and its giver. Continue until every outbound reference resolves.

3. Record the closure evidence

Store stable IDs beside human-readable names. Count unresolved references after each expansion pass. A valid result reaches zero missing endpoints; a partial result should identify the unresolved IDs instead of replacing them with invented text.

4. Export a reproducible boundary

Save the seed, settings, selected IDs, and relationships with the output. A teammate should be able to regenerate the same assembly, compare a revision, or remove one system without guessing which records were connected.

Ship the seed when:

  • Every relationship has a resolvable source and target ID.
  • The same seed and settings reproduce the same selected records.
  • Names are presentation labels; IDs remain the durable join keys.
  • Omitted systems are declared instead of silently approximated.
  • A human can inspect the result before it enters production.
Guide 02

Economy design

8 min read

Merchant economies

A believable shop is a relationship between supply, place, progression, and price.

Random inventory is fast, but it rarely explains why an item is present, what the seller needs, or how the price reacts to the world. A merchant economy becomes reusable when stock selection and pricing are separate, inspectable decisions anchored to canonical item records.

01Catalog valueOne stable baseline per item
→
02Stock fitShop type, region, and tier
→
03Market stateSupply, demand, and scarcity
→
04Trade resultBuy price, buyback, quantity

Separate identity from transaction

The item record owns the name, stable ID, tier, category, and baseline value. The stock record owns seller-specific quantity, markup, demand, and availability. This prevents one sword from becoming five unrelated records just because five merchants price it differently.

Make stock explainable

Give each merchant a region, specialty, and progression tier. Then filter candidate items before weighting them. A harbor apothecary should favor remedies and coastal ingredients because its rules say so, not because the final list was edited by hand.

Layer price modifiers in order

Begin with catalog value, apply the merchant’s normal trading posture, then apply temporary market conditions and player-facing adjustments. Keep each factor visible. Designers can tune one layer without changing the canonical value everywhere else.

Test circulation, not one screen

Trace several items through acquisition, sale, crafting use, and reward sources. Watch for items that enter the economy without a sink, essential materials with no supplier, and reward values that erase the purpose of trade.

A healthy merchant prototype demonstrates:

  • Canonical item IDs shared by stock, recipes, and rewards.
  • Region and tier filters applied before random weighting.
  • Visible buy and buyback calculations.
  • Deterministic stock generation for repeatable testing.
  • At least one item source and one meaningful item sink.
  • Exportable records that retain the calculation inputs.
Guide 03

Engine integration

6 min read

Engine data contracts

Generate models from the complete schema, then protect the IDs that connect the game.

Moving JSON or CSV into an engine is not just a syntax conversion. The durable contract is the combination of field names, inferred types, nullability, nested record shapes, and stable relationship IDs. A useful integration preserves that contract while keeping uncertain fields visible for review.

1. Infer across every record

A first-row generator misses optional fields and accepts accidental types as canonical. Inspect the complete dataset, record every observed type, and mark a field optional when it is absent or null anywhere. Mixed values should produce a warning instead of a confident but fragile model.

2. Sanitize names without losing evidence

JSON keys can contain spaces, punctuation, leading numbers, or engine-reserved words. Convert them into valid identifiers, but retain the original serialized key through an attribute, mapping table, or comment. Silent renaming breaks imports and makes debugging unnecessarily difficult.

3. Treat IDs as references

Fields such as item_id, quest_id, and next_encounter_id are not decorative strings. Index records by stable ID after import, resolve relationships in a separate pass, and fail visibly when a target is missing. Display names can change without invalidating save data or content joins.

4. Separate generated and authored code

Keep generated data models in their own folder or namespace. Put gameplay behavior, validation rules, and project-specific helpers in separate authored files. A schema refresh can then replace generated models without erasing production logic.

Approve the integration when:

  • The generated output is deterministic for the same source and target.
  • Every record group, nested shape, and observed field appears in the schema summary.
  • Reserved and invalid identifiers compile without hiding their original keys.
  • Stable IDs remain explicit and unresolved relationships are reported.
  • Generated files contain data structure only; project behavior remains authored separately.
