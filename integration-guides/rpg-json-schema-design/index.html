Contract design

RPG JSON schema design that remains stable as the game grows

A useful RPG schema does more than deserialize. It gives every authored concept a durable identity, makes relationships visible, defines units and nullability, and leaves room for migrations without corrupting saves.

Step 1

Decide what the JSON owns

Start by separating authored source data from mutable play state. The catalog may define that an emberglass vial has a base value of 48 and belongs to the alchemy category. A save file may record that the player owns three vials and that a particular merchant is out of stock. Those facts have different lifetimes and should not share one record.

Keep source data deterministic and reviewable. A source record should describe design intent: identity, display text, tags, base values, and references to other authored records. Runtime state should describe a playthrough: quantities, cooldowns, discovered flags, generated rolls, and temporary modifiers. Rebuilding the catalog must not reset a save; loading a save must not redefine the catalog.

{
  "schemaVersion": 1,
  "items": [
    {
      "id": "item.emberglass_vial",
      "name": "Emberglass Vial",
      "category": "alchemy",
      "baseValue": 48,
      "tags": ["volatile", "glass"]
    }
  ]
}
Contract rule

If a value can differ between two save files, it probably does not belong in the canonical catalog.

Step 2

Use stable IDs, never array positions

An ID is a promise that the same token will continue to mean the same concept. Use an ASCII format that is easy to compare and safe in filenames, URLs, logs, and source control. A namespaced token such as item.emberglass_vial is more diagnostic than 1047, while an opaque UUID is useful when records are created by distributed tools. Pick one policy and enforce it.

Do not derive IDs from the current display name at runtime. Names are editorial; IDs are relational. Renaming "Minor Health Potion" to "Field Tonic" should change one string, not every recipe, shop row, quest reward, and save reference. Likewise, never use the index in an array as identity. Sorting the array would silently retarget every reference.

FieldGood roleBad role
idPermanent joins and save referencesLocalized display copy

Validate IDs as a set before importing any relationships. Reject missing, blank, duplicate, or malformed IDs. A warning is too weak for duplicates because a dictionary can preserve only one of the colliding records.

Step 3

Represent relationships as explicit IDs

Embed a value when it belongs only to its parent and has no independent identity. Reference a value when several systems must agree on the same concept. A recipe ingredient should usually point to an item ID; a small color swatch used only by one item can be embedded.

{
  "recipes": [
    {
      "id": "recipe.frostward_tonic",
      "outputItemId": "item.frostward_tonic",
      "outputQuantity": 1,
      "ingredients": [
        { "itemId": "item.emberglass_vial", "quantity": 1 },
        { "itemId": "item.winter_mint", "quantity": 3 }
      ]
    }
  ]
}

Use role-specific field names such as outputItemId and merchantId. A generic field called reference hides intent and makes automated validation harder. For one-to-many relationships, store a list of typed reference objects when the edge has its own data, such as quantity, weight, rank, or unlock conditions.

Resolve in two passes. Pass one creates every record and indexes it by ID. Pass two resolves references and reports missing targets with the source record and field path. This supports forward references and produces errors that a content author can act on.

Step 4

Make optionality and units unambiguous

Absence, null, zero, and an empty array are different states. Use absence for a field the record does not support, null for an explicitly empty slot when the consumer supports it, zero for a real numeric value, and an empty array for a valid relationship collection with no members. Do not mix these representations casually.

Write units into names when the unit is not structurally guaranteed: cooldownSeconds, weightGrams, or chanceBasisPoints. Floating-point percentages invite ambiguity between 0.25 and 25. Integer basis points make the scale explicit: 2,500 means 25.00 percent.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["id", "name", "baseValue"],
  "properties": {
    "id": { "type": "string", "pattern": "^item\\.[a-z0-9_]+$" },
    "name": { "type": "string", "minLength": 1 },
    "baseValue": { "type": "integer", "minimum": 0 },
    "cooldownSeconds": { "type": ["number", "null"], "minimum": 0 }
  },
  "additionalProperties": false
}

additionalProperties: false is useful in controlled authoring pipelines because it catches misspellings. During a staged migration, a more permissive reader may be practical, but unknown fields should still be reported so drift does not become invisible.

Step 5

Version semantics, not every edit

Increment the schema version when a consumer must interpret the data differently. Adding a new optional description does not necessarily require a migration. Changing price from coins to copper units does. Store the version at a documented root, keep migrations sequential, and test an old fixture through every supported path.

function migrateCatalog(input) {
  let data = structuredClone(input);
  while (data.schemaVersion < 3) {
    if (data.schemaVersion === 1) data = migrateV1ToV2(data);
    else if (data.schemaVersion === 2) data = migrateV2ToV3(data);
    else throw new Error("Unsupported schema version");
  }
  return data;
}

Never reuse a retired ID for a different item. Keep a small tombstone map if saves can contain removed IDs, and define a policy: replace with a successor, preserve an inert placeholder, or issue a precise load error. Silent substitution turns a data change into player-facing corruption.

Migration trap

Do not mutate source files automatically during game startup. Migrate into memory or through an explicit authoring command so source changes remain reviewable.

Preflight

Schema validation checklist

  • Every authored entity has one stable, unique ID.
  • Display names and file order are never used as foreign keys.
  • Every relationship field names its target role and expected collection.
  • Numeric units and probability scales are explicit.
  • Missing, null, zero, and empty collections have documented meanings.
  • Source data and per-save state live in separate contracts.
  • The root records a semantic schema version.
  • Old fixtures pass deterministic migration tests.
  • Broken references report source ID, field path, and missing target.
