Economy systems

Integrate game economy and shop data without hiding the price math

A durable shop system separates canonical item value, merchant policy, local market pressure, player effects, stock selection, and save state. Each layer can then be tuned and explained without rewriting the catalog.

Architecture

Give each economic fact one owner

The item catalog should own a canonical base value and classification. A merchant profile should own buying and selling posture, accepted categories, budget, and restock policy. A market state should own temporary scarcity or regional modifiers. Player state should own reputation, skills, and one-time discounts. Inventory state should own current quantities and the seed or timestamp needed to reproduce them.

Combining all of those facts into one final price field makes balancing opaque. When a sword costs 312 coins, a designer should be able to see the base value, merchant markup, scarcity multiplier, reputation adjustment, rounding rule, and final clamp. Explainability is a production feature because it turns balance feedback into an actionable change.

Step 1

Join catalogs with stable IDs

Merchant stock rules should reference item IDs or tag constraints, not copy the full item record. Copying values creates competing truths: changing an item's canonical price would leave old merchant rows stale. Stable references keep the catalog normalized while allowing generated inventory entries to snapshot the final quantity and price for one restock cycle.

{
  "items": [
    {
      "id": "item.emberglass_vial",
      "category": "alchemy",
      "baseValue": 48,
      "rarityTier": 2,
      "tags": ["fragile", "volatile"]
    }
  ],
  "merchants": [
    {
      "id": "merchant.cold_lantern",
      "sellMarkupBasisPoints": 12500,
      "buybackBasisPoints": 4200,
      "budgetCoins": 1800,
      "stockRules": [
        { "itemId": "item.emberglass_vial", "weight": 18, "quantity": [1, 4] }
      ]
    }
  ]
}

Basis points avoid the ambiguity between 1.25 and 125. Here, 12,500 basis points means 125 percent of canonical value and 4,200 means 42 percent. Quantity ranges are inclusive by contract. Validate merchant IDs, item IDs, non-negative budgets, bounded multipliers, and quantity ranges before stock generation.

Crafting recipes and rewards also participate in the economy. A recipe references input and output item IDs. A reward row references item IDs and quantities. Those joins let an audit calculate production cost, expected faucet value, and whether merchants sell an output below its ingredient floor.

Step 2

Calculate prices as a visible sequence

Start from the canonical item value. Apply the merchant's normal posture, then market pressure, player effects, and a final rounding rule. Clamp each modifier to a documented range so a data mistake cannot produce negative or extreme prices. Apply taxes or fees in one named layer rather than hiding them inside the markup.

function quoteSellPrice(item, merchant, market, player) {
  const merchantFactor = clamp(merchant.sellMarkupBasisPoints / 10_000, 0.25, 5);
  const marketFactor = clamp(market.factorByItemId[item.id] ?? 1, 0.5, 2.5);
  const reputationFactor = clamp(1 - player.discountBasisPoints / 10_000, 0.5, 1);
  const unrounded = item.baseValue * merchantFactor * marketFactor * reputationFactor;
  const finalCoins = Math.max(1, Math.round(unrounded));
  return { base: item.baseValue, merchantFactor, marketFactor,
    reputationFactor, unrounded, finalCoins };
}

Return a quote object rather than only the final integer. The UI may show a concise price, while debug tools and balance reports can show the full path. Use one pricing service for buying, tooltips, transaction checks, and automated simulations so displayed and charged values do not diverge.

Buyback prices need their own policy and a strict relationship to selling prices. Unless arbitrage is intentional, the amount a merchant pays the player should remain below the amount that same merchant charges after all modifiers. Test unusual combinations of reputation, regional demand, taxes, and perks.

Rounding trap

Round once at the end. Rounding after every multiplier can create inconsistent results and exploitable buy-sell loops near price boundaries.

Step 3

Make stock generation deterministic and constrained

A stock generator should accept an explicit seed plus immutable inputs: merchant ID, restock cycle, world state, and eligible item rules. The same inputs should produce the same stock. Determinism makes a reported inventory reproducible, supports save/load, and prevents opening the menu repeatedly from rerolling rare items.

Filter eligibility before weighted selection. Category, tier, location, quest, and uniqueness constraints determine candidates. Then select according to the documented roll model. Apply per-item and total-slot caps, calculate quantities, and reserve enough merchant budget if buyback or procurement is simulated.

function restockSeed(worldSeed, merchantId, cycle) {
  return stableHash(`${worldSeed}|${merchantId}|${cycle}`);
}

function eligibleItems(catalog, rule, worldState) {
  return catalog.items.filter(item =>
    (!rule.category || item.category === rule.category) &&
    item.rarityTier <= rule.maximumTier &&
    !worldState.uniqueItemsSold.has(item.id));
}

Persist the cycle and generated stock or persist enough inputs to regenerate it exactly. Do not use wall-clock time directly as the only seed. Time zones, paused games, and clock changes make that behavior difficult to test. Convert time to a named restock cycle under project control.

Define depletion behavior. A merchant may keep sold-out rows visible, remove them, or substitute another item. Purchases must update save-owned stock atomically with currency. Catalog definitions remain immutable.

Step 4

Audit faucets, sinks, and conversion loops

Prices only make sense relative to acquisition rates. Estimate currency and item value entering the game from encounters, quests, salvage, and repeatable activities. Compare that with required and optional sinks: equipment, consumables, crafting fees, repairs, travel, upgrades, and cosmetics. Track expected value per unit of player time, not only per event.

function expectedLootValue(entries, itemById) {
  return entries.reduce((sum, row) => {
    const probability = row.weight / entries.reduce((s, x) => s + x.weight, 0);
    const averageQuantity = (row.minQuantity + row.maxQuantity) / 2;
    return sum + probability * averageQuantity * itemById.get(row.itemId).baseValue;
  }, 0);
}

The example assumes a weighted single pick and uniform integer quantity range; other roll models need different math. Label every assumption. A repeatable encounter with expected value 60 that takes one minute is economically different from a one-time quest paying 600 after thirty minutes.

Audit conversion loops across systems. Buying inputs, crafting outputs, and selling them back should not generate infinite currency unless the loop is a deliberate reward. Include fees, yields, critical crafting outcomes, reputation discounts, and regional modifiers. Use stable IDs to traverse the actual recipe and shop relationships instead of comparing names.

Step 5

Test invariants and balance scenarios

  • Every merchant, stock, recipe, and reward reference resolves by stable ID.
  • All basis-point fields use documented ranges and meanings.
  • Pricing returns inspectable intermediate factors.
  • Rounding occurs once under one shared rule.
  • Buyback cannot exceed the matching sale quote accidentally.
  • Identical restock inputs produce identical inventories.
  • Eligibility is applied before weighted selection.
  • Unique and sold-out state belongs to the save, not the catalog.
  • Expected faucet value includes quantity and repetition rate.
  • Craft-buy-sell loops are tested under extreme modifier combinations.
  • Missing data produces a controlled error, not a zero-price item.
  • Balance reports record catalog and economy rule versions.

Use small scenario fixtures in automated tests: a baseline merchant, maximum discount player, scarce market, abundant market, empty eligible set, sold-out unique item, and a deliberately exploitable recipe. Then run broader simulations with fixed seeds and compare summary outputs under review.
