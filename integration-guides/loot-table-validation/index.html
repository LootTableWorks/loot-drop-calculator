Probability QA

Validate loot tables before players discover the math is broken

A table can total 100 and still be wrong. First identify the roll model, then validate structure, calculate exact outcomes, run seeded simulations, and compare observed results with statistically reasonable ranges.

Step 1

State what one roll means

"Chance" is incomplete without a selection model. In a weighted single-pick table, one row wins and its probability is its weight divided by the sum of positive weights. In an independent-drop table, every row receives its own roll, so several items or no items can drop. In a pick-without-replacement table, several distinct rows win and later probabilities depend on earlier picks.

ModelPossible result from one eventCore calculation
Weighted single pickExactly one eligible rowweight / totalWeight
Independent dropsZero, one, or many rowsEach row uses its own probability
Weighted picks with replacementFixed count; duplicates possibleRepeat the single-pick distribution
Weighted picks without replacementFixed count; distinct rowsRecalculate after each removal

Do not place a field called chance in one table and interpret it as a relative weight in code. Name fields according to semantics: weight, dropChanceBasisPoints, or guaranteedQuantity. If a table includes a no-drop outcome, model it explicitly as a row or define it as the remaining probability by contract.

{
  "id": "loot.bandit_scout",
  "rollModel": "weighted_single_pick",
  "rolls": 1,
  "entries": [
    { "itemId": "item.copper_marks", "weight": 60, "quantity": [4, 9] },
    { "itemId": "item.field_tonic", "weight": 25, "quantity": [1, 1] },
    { "itemId": "item.smoke_salt", "weight": 10, "quantity": [1, 2] },
    { "itemId": null, "weight": 5, "quantity": [0, 0] }
  ]
}

Step 2

Reject structural faults before doing probability math

Every table needs a stable ID, recognized model, valid roll count, and non-empty entry list. Every reward row needs either a resolvable target ID or an explicit no-drop marker. Weights must be finite and non-negative; independent chances must stay inside the documented scale. Quantity minima cannot exceed maxima.

Zero-weight rows are unreachable. That may be intentional for disabled content, but the state should be explicit rather than silently shipping dead rows. Negative weights, NaN, infinity, duplicate row IDs, missing item references, and a total positive weight of zero are hard failures.

function validateWeightedTable(table, knownItemIds) {
  const issues = [];
  let positiveWeight = 0;
  for (const [index, row] of table.entries.entries()) {
    const path = `entries[${index}]`;
    if (!Number.isFinite(row.weight) || row.weight < 0)
      issues.push(`${path}.weight must be finite and non-negative`);
    else positiveWeight += row.weight;
    if (row.itemId !== null && !knownItemIds.has(row.itemId))
      issues.push(`${path}.itemId is missing: ${row.itemId}`);
    if (row.quantity[0] > row.quantity[1])
      issues.push(`${path}.quantity minimum exceeds maximum`);
  }
  if (positiveWeight <= 0) issues.push("table has no selectable weight");
  return issues;
}
Total-100 myth

Relative weights do not need to total 100. Forcing them to 100 can add rounding drift without improving the distribution. Validate the model, not a cosmetic total.

Step 3

Calculate exact per-roll outcomes

For a weighted single pick, divide each positive row weight by the total. The example total is 100, so the field tonic is 25 percent. If all weights were doubled, the probabilities would remain unchanged. Display enough precision to explain the result, but keep the source weights as authored integers when possible.

function weightedProbabilities(entries) {
  const total = entries.reduce((sum, row) =>
    sum + (row.weight > 0 ? row.weight : 0), 0);
  if (total <= 0) throw new Error("No positive loot weight");
  return entries.map(row => ({
    itemId: row.itemId,
    probability: Math.max(0, row.weight) / total
  }));
}

For independent drops, sum is not constrained to 100 percent. Three independent items at 50 percent can all drop together. Expected item count is the sum of individual probabilities, but that is an average, not a guarantee. To find the chance of no drops, multiply each failure probability. The chance of at least one drop is one minus that product.

function chanceOfAtLeastOne(independentChances) {
  const chanceOfNone = independentChances.reduce(
    (product, p) => product * (1 - p), 1);
  return 1 - chanceOfNone;
}

Step 4

Handle repeated rolls without adding probabilities

If an item has probability p on each independent repeated roll, the chance of obtaining it at least once in n rolls is 1 - (1 - p)^n. Adding p repeatedly is only an approximation at very small probabilities and quickly becomes impossible values above 100 percent.

At a 5 percent per-roll chance, 10 independent attempts yield about a 40.13 percent chance of at least one success, not 50 percent. Expected successes are still 0.5. Probability of at least one and expected count answer different design questions.

function atLeastOne(perRollProbability, rolls) {
  if (perRollProbability < 0 || perRollProbability > 1)
    throw new RangeError("Probability must be between 0 and 1");
  if (!Number.isInteger(rolls) || rolls < 0)
    throw new RangeError("Roll count must be a non-negative integer");
  return 1 - Math.pow(1 - perRollProbability, rolls);
}

Without-replacement selection requires conditional math. Removing a selected row changes the remaining total, so do not reuse the original probabilities for later picks. Define what happens when the requested pick count exceeds the number of positive eligible rows.

Step 5

Use simulation as an audit, not as the source of truth

Exact math should define simple models. Simulation verifies implementation, exposes complex conditional systems, and communicates long-run behavior. Use a seeded pseudo-random generator so failures can be reproduced. Record the seed, roll count, table version, and algorithm version with the result.

Compare observed counts with an expected range rather than demanding an exact percentage. For a binomial outcome with probability p over n independent rolls, the standard deviation of the count is the square root of n * p * (1 - p). A rough three-standard-deviation band is a practical automated warning, not proof of correctness.

function auditCount(observed, rolls, probability) {
  const expected = rolls * probability;
  const sigma = Math.sqrt(rolls * probability * (1 - probability));
  return {
    expected,
    observed,
    withinAuditBand: Math.abs(observed - expected) <= 3 * sigma
  };
}

A simulation can match expected frequencies while still selecting the wrong item IDs if data joins are broken. Audit both distribution and identity. Also test fixed boundary random values such as zero and the value immediately below one to catch cumulative-range errors.

Step 6

Model pity, guarantees, and eligibility explicitly

Progression controls change the probability model and should be visible in data. A pity counter may raise weight after each failure, guarantee a category on a threshold, or replace the next roll. Specify whether the counter is per table, per item, per account, or per event, and when it resets.

Eligibility filters such as player level, quest state, biome, or first-clear status must run before weight normalization. Removing ineligible rows after selection biases results or causes rerolls with unclear odds. Produce an eligible candidate list, validate its total, then roll.

  • The roll model is named in the table contract.
  • Every target item ID resolves against the canonical catalog.
  • Weights and chances use explicit, validated scales.
  • Zero-weight and unreachable rows are reported.
  • Exact probabilities are calculated before simulation.
  • Repeated-roll displays use complementary probability.
  • Seed, table version, and algorithm version make simulations reproducible.
  • Eligibility is applied before normalization.
  • Pity and guarantee reset rules are documented and tested.
  • Economy audits multiply drop rates by quantities and item values.
