TypeScript boundary

Build TypeScript RPG data models that do not trust raw JSON

Interfaces disappear at runtime. A safe integration parses JSON as unknown, validates it at one boundary, converts it into readonly domain types, and uses branded stable IDs to prevent accidental cross-collection joins.

Boundary rule

JSON.parse returns evidence, not a trusted model

A TypeScript annotation cannot validate a runtime value. Casting JSON.parse(text) as Catalog only suppresses compiler questions; it does not prove that IDs exist, arrays contain the expected records, numbers are finite, or references point to valid targets. Treat parsed data as unknown until a runtime check establishes the contract.

export function parseJson(text: string): unknown {
  if (new TextEncoder().encode(text).byteLength > 5_000_000) {
    throw new Error("RPG data exceeds the 5 MB import limit.");
  }
  try {
    return JSON.parse(text) as unknown;
  } catch {
    throw new Error("RPG data is not valid JSON.");
  }
}

Keep validation near the boundary. Once a value has been validated and converted, application code should not repeatedly ask whether item.id is a string. A narrow boundary gives the rest of the codebase a stronger invariant and keeps error reporting consistent.

False confidence

A type assertion changes no runtime behavior. If the source can change independently from the code, it needs a runtime contract.

Step 1

Separate wire DTOs from domain types

The wire model mirrors the serialized field names and optionality. The domain model reflects the guarantees your game wants after import. This lets you support an old schema, normalize nullable values, parse units, and rename fields without spreading compatibility logic through gameplay code.

{
  "schemaVersion": 1,
  "items": [
    {
      "id": "item.emberglass_vial",
      "name": "Emberglass Vial",
      "baseValue": 48,
      "tags": ["alchemy", "fragile"]
    }
  ],
  "recipes": [
    {
      "id": "recipe.frostward_tonic",
      "outputItemId": "item.frostward_tonic"
    }
  ]
}
type WireItem = {
  id: string;
  name: string;
  baseValue: number;
  tags?: string[];
};

type WireRecipe = {
  id: string;
  outputItemId: string;
};

type WireCatalog = {
  schemaVersion: 1;
  items: WireItem[];
  recipes: WireRecipe[];
};

Wire types are documentation for validator authors; they still do not validate. Keep them narrow, and avoid any. If a field intentionally accepts more than one representation during migration, model that union and normalize it immediately.

Step 2

Collect field-path issues with small predicates

A dependency-free validator can be concise if it uses reusable checks. Start with isRecord, then verify required fields and array elements. Return structured issues rather than only booleans when content authors need useful feedback.

type Issue = Readonly<{ path: string; message: string }>;

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null && !Array.isArray(value);
}

function readString(row: Record<string, unknown>, key: string, path: string,
  issues: Issue[]): string | undefined {
  const value = row[key];
  if (typeof value !== "string" || value.trim() === "") {
    issues.push({ path: `${path}.${key}`, message: "Expected a non-empty string" });
    return undefined;
  }
  return value;
}

Validate finite numbers with Number.isFinite, integer requirements with Number.isInteger, and arrays by checking every member. Do not validate only the first row. Fields that appear later, mixed types, and missing required values are precisely the failures a complete scan should expose.

function validateRoot(value: unknown): Issue[] {
  const issues: Issue[] = [];
  if (!isRecord(value)) return [{ path: "$", message: "Expected an object" }];
  if (value.schemaVersion !== 1)
    issues.push({ path: "$.schemaVersion", message: "Expected schema version 1" });
  if (!Array.isArray(value.items))
    issues.push({ path: "$.items", message: "Expected an array" });
  else value.items.forEach((row, index) => validateItem(row, `$.items[${index}]`, issues));
  return issues;
}

Step 3

Brand IDs and make imported definitions readonly

All IDs are strings at runtime, but TypeScript can prevent many accidental joins at compile time. Brand each ID family so a merchant ID cannot be passed to an item lookup without an explicit mistake. The branding function should remain private to the validated conversion boundary.

declare const itemIdBrand: unique symbol;
declare const recipeIdBrand: unique symbol;

export type ItemId = string & { readonly [itemIdBrand]: true };
export type RecipeId = string & { readonly [recipeIdBrand]: true };

export type ItemDefinition = Readonly<{
  id: ItemId;
  name: string;
  baseValue: number;
  tags: readonly string[];
}>;

function toItemId(value: string): ItemId {
  return value as ItemId; // Called only after ID validation.
}

Use Readonly and readonly arrays for definitions so gameplay systems do not mutate canonical content by accident. Mutable inventory entries should store an item ID and quantity separately. Freeze objects at runtime only if your threat model or debugging needs it; TypeScript's readonly modifier is a compile-time guarantee.

Normalize at conversion: trim allowed strings, fill optional arrays with empty arrays, convert enum tokens through a closed lookup, and reject invalid ranges. Do not silently coerce "48" into 48 unless the schema explicitly supports that migration.

Step 4

Index complete collections before resolving joins

A Map makes duplicate detection and lookup intent explicit. Build every primary collection first. Then convert relationship rows and resolve their stable IDs. Keep both the target ID and resolved object when persistence or diagnostics need the token.

function indexItems(items: readonly ItemDefinition[]): ReadonlyMap<ItemId, ItemDefinition> {
  const result = new Map<ItemId, ItemDefinition>();
  for (const item of items) {
    if (result.has(item.id)) throw new Error(`Duplicate item ID: ${item.id}`);
    result.set(item.id, item);
  }
  return result;
}

function requireItem(items: ReadonlyMap<ItemId, ItemDefinition>,
  rawId: string, sourcePath: string): ItemDefinition {
  const id = toItemId(rawId);
  const item = items.get(id);
  if (!item) throw new Error(`${sourcePath} references missing item ${rawId}`);
  return item;
}

Do not expose a mutable map from the catalog API. TypeScript's ReadonlyMap communicates intent, though the underlying object can still be mutated by code that retains the original reference. Build indexes inside the catalog factory and keep writable references private.

Save-file rule

Persist stable IDs, not serialized runtime objects. Resolve IDs against the current catalog during load and apply a documented missing-content policy.

Preflight

Test the validator and the domain conversion independently

  • Malformed text fails before contract validation.
  • Non-object roots and unsupported versions produce field-path issues.
  • Every array member is validated, not only the first record.
  • Blank, malformed, and duplicate stable IDs fail conversion.
  • NaN, infinity, fractions, and negative values are checked by field policy.
  • Optional arrays normalize to readonly empty arrays.
  • Wrong ID families fail TypeScript compilation in type tests.
  • Forward references resolve after complete indexing.
  • Broken joins report source path and missing target ID.
  • Source order does not alter catalog semantics.
  • Imported definitions cannot be mutated by application code.
