Import RPG JSON with Unity JsonUtility and stable IDs

JsonUtility is fast and dependency-free, but it is deliberately narrow. Use it for transport objects, then build the runtime model, indexes, and reference checks yourself.

14 minute readUpdated July 21, 2026Unity C# + JSON

Before code

Use JsonUtility for the shape it supports

Unity's JsonUtility maps JSON fields onto serializable C# fields. It is a good fit for predictable data transfer objects with public fields, arrays or lists, nested serializable classes, strings, numbers, booleans, and enums represented according to your conversion policy. It is not a general JSON document API.

Plan around the constraints. A top-level JSON array needs a wrapper object. Dictionaries are not directly represented, polymorphic graphs need a different approach, JSON property names must match serialized field names, and missing fields fall back to C# defaults. A missing integer and an authored zero therefore look identical unless the contract carries an explicit presence marker or the source is validated before import.

JsonUtility can return an object even when a field is absent. Validate the source contract and check required fields after deserialization.

Step 1

Wrap arrays and keep DTOs boring

The JSON contract should have one root object with a schema version and named collections. Transport classes should mirror that wire format exactly. Avoid gameplay methods, Unity object references, and computed properties in DTOs. Their job is to cross the serialization boundary and preserve evidence for validation.

{
  "schemaVersion": 1,
  "items": [
    {
      "id": "item.emberglass_vial",
      "name": "Emberglass Vial",
      "baseValue": 48,
      "tags": ["alchemy", "fragile"]
    }
  ],
  "recipes": [
    {
      "id": "recipe.frostward_tonic",
      "outputItemId": "item.frostward_tonic",
      "ingredientItemIds": ["item.emberglass_vial"]
    }
  ]
}
using System;

[Serializable]
public sealed class CatalogDto
{
    public int schemaVersion;
    public ItemDto[] items;
    public RecipeDto[] recipes;
}

[Serializable]
public sealed class ItemDto
{
    public string id;
    public string name;
    public int baseValue;
    public string[] tags;
}

[Serializable]
public sealed class RecipeDto
{
    public string id;
    public string outputItemId;
    public string[] ingredientItemIds;
}

Keep field names synchronized with JSON. If your C# conventions require PascalCase, convert into a separate runtime class rather than changing the wire DTO. This cleanly isolates schema compatibility from application style.

Step 2

Fail early with a narrow import result

Load text from a trusted project asset or an explicitly selected local file. Do not let authored JSON choose arbitrary project paths or types to instantiate. Parse once, collect all actionable validation issues, and return either a complete catalog or a failure result. A partially valid global catalog is difficult to reason about.

using System;
using System.Collections.Generic;
using UnityEngine;

public static class CatalogImporter
{
    public static Catalog Import(string json)
    {
        if (string.IsNullOrWhiteSpace(json))
            throw new ArgumentException("Catalog JSON is empty.");

        var dto = JsonUtility.FromJson<CatalogDto>(json);
        if (dto == null) throw new FormatException("Catalog root is invalid.");
        if (dto.schemaVersion != 1)
            throw new NotSupportedException($"Schema {dto.schemaVersion} is not supported.");
        if (dto.items == null) throw new FormatException("items is required.");

        return Catalog.Build(dto);
    }
}

For player-facing builds, catch the exception at the composition boundary and display a controlled error. In editor tooling or CI, include the source file, record ID, and field path. Do not log the entire imported document; concise diagnostics are more useful and avoid exposing content unnecessarily.

Set explicit input size limits if the file can come from outside the project. A static catalog should not allocate unbounded text or arrays. Limits belong both before parsing and in product documentation.

Step 3

Build indexes first, resolve references second

Runtime code wants efficient lookups and typed relationships. Build those structures after deserialization. First convert and index every item by stable ID. Reject blank or duplicate IDs. Then convert recipes and resolve their item IDs against the completed index. This handles forward references without making file order meaningful.

public sealed class Catalog
{
    public IReadOnlyDictionary<string, ItemDefinition> Items => _items;
    private readonly Dictionary<string, ItemDefinition> _items = new();
    private readonly List<RecipeDefinition> _recipes = new();

    public static Catalog Build(CatalogDto source)
    {
        var result = new Catalog();
        foreach (var row in source.items)
        {
            RequireId(row?.id, "items[].id");
            if (!result._items.TryAdd(row.id, new ItemDefinition(
                row.id, row.name ?? row.id, row.baseValue, row.tags ?? Array.Empty<string>())))
                throw new FormatException($"Duplicate item ID: {row.id}");
        }

        foreach (var row in source.recipes ?? Array.Empty<RecipeDto>())
        {
            RequireId(row?.id, "recipes[].id");
            var output = Resolve(result._items, row.outputItemId, row.id, "outputItemId");
            var ingredients = new List<ItemDefinition>();
            foreach (var id in row.ingredientItemIds ?? Array.Empty<string>())
                ingredients.Add(Resolve(result._items, id, row.id, "ingredientItemIds"));
            result._recipes.Add(new RecipeDefinition(row.id, output, ingredients));
        }
        return result;
    }
}

Keep the original stable ID on runtime definitions even after resolving object references. IDs are essential for save files, logs, deterministic tests, debugging, and reconnecting content after a reload. Unity instance IDs and array indices are not substitutes because they are not stable across builds or sessions.

Error design

A useful broken-reference message reads: recipe.frostward_tonic.outputItemId - missing item.frostward_tonic. It names the source, field, and target.

Step 4

Choose when imported data becomes a Unity asset

There are two common workflows. Runtime import keeps external JSON as the source of truth and rebuilds indexes on startup. Editor import converts validated DTOs into ScriptableObject assets before a build. Runtime import is simpler for moddable or frequently updated data. Editor import provides native references, inspector browsing, and build-time validation.

If you generate ScriptableObjects, make the generation command explicit and deterministic. Store the stable source ID on each generated asset. Update assets by ID rather than filename, and keep generated output in its own folder. Do not place authored edits in generated assets because the next import will overwrite them.

#if UNITY_EDITOR
// Conceptual import boundary: JSON is authoritative, assets are generated.
public static void RebuildCatalogAssets(TextAsset source)
{
    Catalog catalog = CatalogImporter.Import(source.text);
    foreach (ItemDefinition item in catalog.Items.Values)
        UpsertGeneratedItemAsset(item.Id, item);
    RemoveGeneratedAssetsNotPresentIn(catalog.Items.Keys);
}
#endif

Whether import occurs at runtime or in the editor, never call Resources.Load using a path supplied by the JSON. Keep content identity and asset location as separate mappings owned by the project.

Preflight

Test the import boundary, not only happy data

  • A valid fixture imports with the expected schema version and counts.
  • An empty document and malformed JSON fail with controlled errors.
  • A top-level array is rejected when the wrapper contract is required.
  • Blank and duplicate stable IDs fail before relationship resolution.
  • Forward references resolve because indexes are built first.
  • Missing relationship targets name the source ID and field.
  • Missing optional arrays become empty collections by policy.
  • Unsupported schema versions fail before runtime objects are created.
  • Reordering source arrays does not change relationship targets.
  • Two imports of the same fixture produce equivalent runtime catalogs.
